# Her World

这里只写产品现在的样子和阶段规划，历史交给 git。结构见 [architecture.md](architecture.md)，拍板过的取舍见 [decisions.md](decisions.md)。

## 给谁用

- 主人自己：Her World 的所有者和唯一使用者。
- 其次是读代码、维护它的 Claude 和 Codex。

## 核心场景

Her World 是跑在 DSH 里的伙伴插件，同一个伙伴的身份、记忆和生活贯穿各个入口：

1. 在 DSH 原生聊天里和伙伴说话，她记得以前聊过的事。
2. 桌宠（Desktop）和 Room 里能看到她在做什么、心情怎样，也能在那里和她聊天。
3. 她有自己的生活：身体状态、照料、种地、钱包背包、阅读、计划、回顾和日记。
4. 通过 QQ、微信等渠道和语音找到她。
5. 在 DSH 的插件详情页一键更新。

## 解决什么问题

这次重构前，模块边界有三处典型问题。

- Core 反向引用上层模块（桌宠外观、Life 偏好、情绪文件、记忆目录）。
- Life、Behavior、Economy 互相缠绕，实际是同一件事却被切开。
- Room 直接拿 Desktop 的模块，控制台什么都认识。

改一处牵一片，促成了这次**整体重构**，范围见[阶段 1 缩小决定](decisions.md#2026-11-18-阶段-1-缩小m3-改为收口并发版)，职责和依赖边界见[三层架构](architecture.md#0-一页总览)。

**一句话 MVP**：立起三层边界和自动依赖检查，第一层改用登记口（来源适配、能力状态、工具声明），跑通「备份 → 迁移 → 可回滚」；从 0.1.8 升级到新版后，聊天和记忆照常可用，从旧测试里拆出的行为清单逐条通过。

## 不做什么

- 不加新功能或新玩法。重构期间的新需求记进 `~/Developer/project-design/ideas/inbox.md`，重构结束后再排。
- 不换掉 DSH 的插件体系，不改 DSH 本身。
- 不拆成多个 npm 包（留到边界稳定之后）。
- 不改 npm 包名 `her-world` 和插件的 bundle ID，保证 DSH 里的更新按钮照常可用。
- 包的对外入口、Cordis 服务名、配置项也保持稳定；确需改动的单独找主人拍板，并在已安装环境里验证升级路径。完整清单见 [architecture.md](architecture.md) 6.1。

## 重构的成功标准

- 改一个功能不再牵一片：比如调种地规则，只动「生活世界」。
- 看一页架构图就能读懂各块职责。
- Room、Channels 等外围模块能整个关掉，不影响聊天和记忆。

## 重构的风险

1. 重写时丢掉旧的特殊情况（种地时钟、去重、日记恢复等）。修复批次的口径和证据见[故障家族](#故障家族)；对策是行为清单。
2. 数据迁移出错，影响唯一的真实数据。对策：迁移与回退演练，见 [architecture.md](architecture.md) 第 7 节。
3. 「生活世界」内的职责容易交缠。三区的归属和调用边界见[架构 2.3](architecture.md#23-第二层生活世界管什么)。
4. 战线长：重写期间，旧版仍要修 bug。对策：见「旧版修 bug 的规则」。
5. 回退受限：现有恢复器要求安装包文件指纹完全一致，只覆盖指定目录；新版运行期间新增的聊天不会自动合并回旧记忆库。
6. DSH 自身升级可能改变插件机制，影响新骨架。本计划假设重构期间 DSH 的插件接口基本稳定，需要持续关注。

## 待验证的假设

- 三层切分在代码里成立：合并后，Room、Desktop 能只靠 contracts 读生活世界的状态。
- 阶段 3 收尾时 `tests/` 有 186 个自动测试入口（59 个 `*.test.ts`、127 个 `*.test.mjs`，编译产物只计一次）。入口按 `scripts/checks/verify.mjs:13–17` 的收集规则盘点，详见体检第 2 节。逐条改用公开边界时，仍须核对原行为断言是否保留。
- 不改包名和 bundle ID，已安装的环境能无缝升级到新版；关闭外围模块不影响聊天和记忆（目前只有源码上的依据，需要在隔离的已安装环境里用真实数据副本演练）。
- 全部真实数据（含浏览器里的经济待确认请求）能完整迁移并回滚（需要停写后的真实副本清单和演练）。
- 重写后维护成本真的降低（用「典型修改前后对比」衡量）。

## 重构的度量与机制

**怎么用这一节：**

- **不估时间。** 每个阶段靠完成标准和停止条件管，不靠日期。
- **每个阶段结束都做三件事**：跑行为清单和门禁，全绿才算完成，并至少走通一条从真实入口开始的完整流程（G9）；更新「典型修改前后对比」；主人验收体验，决定继续、调整还是停下。
- **每个阶段里的具体任务**按大改单独写方案：Claude 写、Codex 挑刺，写进 `docs/plans/`，主人同意后才交给 Codex 实现。
- **先搬后改。** 一个步骤要么只搬家（行为不变，行为清单全绿），要么只改逻辑，不在同一步里同时做。
- **发版粒度**：一个版本只装一个能独立验收、发布和回退的交付单位。

### 行为清单

从旧测试里拆出的「必须保住的行为」。索引在 [tests/behavior-list/index.json](../tests/behavior-list/index.json)，测试及公共夹具在 `tests/behavior-list/`，新用例的源码适配入口集中在 `entries.ts`；索引也复用部分原测试。构建前提、清单命令及直接运行入口见 [开发说明](development.md#architecture-behavior)。

- **L1 完整流程**：插件入口加假原生宿主和假模型，覆盖准入、工具限制、执行、落盘、查询或召回及重启恢复。
- **L2 公开面行为**：经公开服务、原生事件和磁盘边界驱动，不构造内部类、不替换私有方法、不读取私有状态。
- **L3 回归参考**：保留在全量门禁，不算清单完成项，也不由清单运行器执行。

阶段 3 收尾时索引有 173 项，分为 L1 64 项、L2 106 项、L3 3 项，清单执行前两级的 170 项（`tests/behavior-list/index.json:2–8`、`scripts/checks/run-behavior-list.mjs:39–43`）。条目的特殊情况、故障家族和会话策略覆盖也登记在索引里。每类补足 L1 的计划阶段见索引的 `l1Stage`，M1 的完成线是每类至少一条 L1 或 L2、每个故障家族一条 L1。

调研列出的 15 类特殊情况，各有对应的旧测试：计划续行、同请求重试不重复生效、效果已落盘后结算失败再重启（`tests/life/life-domain-integration.test.ts`，混合文件，保留行为断言、换掉故障注入的做法）、睡眠中投喂的终态、种地时钟不倒退、离线消耗额度、日记按原日期恢复、历史日记保护、输入持久化先于确认、送达与记忆召回分开、阅读必须有真实文本、QQ 收件恢复、换目录时在途请求不写旧目录、隐藏后取消显示定时器、缺库不得空白替代。

规则：

- 清单在旧代码上必须**全绿**，才能作为新版的验收。
- 新版每个阶段结束，与该阶段相关的条目必须全绿；**整份清单在阶段 4 结束时全绿**。
- 条目只能增加或修订（要说明理由），不能为了通过而删除。
- 每一类至少有一条**从真实入口走完整条流程**的用例（入口 → 准入 → 工具限制 → 执行 → 落盘 → 查询或召回 → 重启恢复）。例如：自主回顾能写日记、主人聊天补写历史日记也能写；计划步骤完成后自动续下一步；互动送达后在另一个会话里能召回；关闭后晚到的录音不再生效。
- 旧测试待重新分类，B 批的 L1/L2/L3 分级是新的分类；行为断言随对应阶段逐步拆出，阶段 1 先守住上述 M1 完成线。
- 验收按索引里的行为及层次判断，不按文件个数替代。

### 「要不要重写」的判断尺度

一个模块出现下面任一条时才重写，否则整体搬进新骨架、不改内容：

- **满足不了依赖规则**：R1–R4 对它报违规，且只靠挪文件、改 import 解决不了。
- **无法单独理解、单独测试**：其测试必须启动其他模块的真实实现才能跑；或手写文件（不含生成文件）超过 **1500 行**时，必须先评估拆分。超过此阈值的手写文件由 `pnpm run metrics` 报告。

### 防止越做越乱的机制

混乱主要来自「范围扩大后拥有者和验收没有跟着收口」和「局部修好、检查通过，又继续叠下一批」。下面这些机制把「变乱」变成能被马上发现、能被叫停的事。

| 编号 | 机制 | 做法 | 落点 |
| --- | --- | --- | --- |
| G1 | **违规棘轮（永久门禁）** | 见 [architecture.md](architecture.md) 第 3 节的「棘轮」 | M1 建立，进入门禁，之后一直生效 |
| G2 | **方案准入问题** | 每份方案加一节「概念与扩展检查」：新增或修改了哪些概念？拥有者是谁？有没有新增词表？复用了哪些已有声明？层间接口有没有变化？**为什么需要这个新职责，对应哪个已确认的用户场景？** 扩大范围的方案还要写清：新增目标替换或延期了什么，当前闭环怎么验收，原完成标准是否作废。审查时对照这一节，并用 R8 报告核对 | M1 起所有方案 |
| G3 | **故障家族复盘** | 按业务流程或不变量归组（不按目录：日记链路横跨 Core、Life 和上游库），计修复批次（同一个提交里的多轮返工也算）。同一个不变量第二次失守就提前复盘；第 3 批相关修复前必须复盘（共同根因、受影响的其他入口、哪条完整流程验证能结束这一轮）。14 天只作报表窗口，不是重新计数的豁免。阈值没有历史校准依据，暂定 | 每个阶段 |
| G4 | **范围冻结** | 阶段内的新想法一律进 `ideas/inbox.md`，不插队；每个阶段只做完成标准里写的事；新增功能须单独立项，或进入下一阶段的完成标准，由主人拍板，并按 G2 重定阶段和验收 | 全程 |
| G5 | **自动度量** | 统计各规则的违规数、词表重复关系和裸字段、`kind`／`action` 判断、超过 1500 行的手写文件和模块间依赖数。阶段收尾和发版前查看报告 | `pnpm run metrics`，只报告 |
| G6 | **`AGENTS.md` 一页入口** | 一页：三层架构图、概念表、「新增东西去哪里登记」。控制在 10 KB 以内（暂定），内容链接到 [architecture.md](architecture.md) 和 `layers.json`，不手抄 | M1 |
| G7 | **规则要有案例** | 每条检查和规则写明对应的真实案例，对应不上的不加 | 全程 |
| G8 | **阶段末复盘规则** | 只有保护目标已经消失、已被更可靠的检查替代、或持续误报且没有有效案例时，才删除或放宽。「整个阶段零报警」不是删除理由 | 每个阶段 |
| G9 | **完成标准含真实流程** | 每个阶段的完成标准至少包含一条从真实入口走完整条流程的验证。每个模块自己的测试各自通过，不能代替这条。反复出现的缺口都是这一类：自主回顾能写日记，主人聊天补写却被另一层守卫拒绝；计划步骤完成后不自动续下一步；互动已送达，在另一个会话里却召回不到 | 每个阶段 |

**必须 / 可后置**：必须的是 G1、G2、G3、G9，以及行为清单、迁移演练和里程碑评审点；可后置的是 G6；G5 由命令输出。

**这些机制抓不住、要靠人判断的**：初始范围本身就过宽，或需求本身不必要（G2 里「对应哪个用户场景」是唯一的防线）；合法接口内部的行为错误（靠 G9 和行为清单）。

### 旧版修 bug 的规则

- 先把会失败的测试写进行为清单，再修在当前主线。
- 修的如果是正被替换的模块，修复和测试一起并入新实现，不在旧、新两处各修一次；该替换单位的完成标准里核对这条测试通过。
- 只修 bug，不顺手加功能（G4）；同一分支同一时间只有一个 Agent 写。
- 同一个 bug 反复在不同入口出现，按 G3 处理。

### 故障家族

**修复批次如何数：** 一个不变量的一轮修复记一批（F）；一个提交里的不同不变量或有证据的再次返工分别记，附随测试、生成基线、结果文档和合并不重复记。功能（N）、发版（P）、其他（O）同样按交付批次去重。分类依据是提交说明、源码/测试差异和保存的执行结果，拿不准的已标估计；没有记录的轮次不补猜。

**阶段 3 修复批次占比估计为 14 / 23（60.9%）。** 分母包括 7 个实施批、2 次发布和 14 个可辨认修复轮次（体检第 7 节）。实施中 6 轮是 Compact 取消、Room 写前取消、绑定代次首轮、桌宠投喂、Console 路由撤销／重复登记和钱包旧页竞写及停写。审查返工 7 轮是绑定代次、回包与实际效果、钱包离线同轮证据、身体呈现、计划读取失败仍停自治、Room 开窗隔离和 Compact 语音取消（`6dd3e4c:docs/plans/stage3-presentation.md:205–232`）。发布后钱包声明路线解决生产迁移阻断，再计 1 轮（`ebf53f1`）。合并历史里未保留的轮次待核实。

#### 绑定代次的 G3 复盘

- **不变量。** 异步任务只在准入时捕获的绑定代次内继续派发、写入、通知与回包。A→B→A 后，旧 A 和新 A 即使工作区、路径、存储 ID、修订都相同，旧 A 的任务也不能继续。已提交的效果按原号核对。已经派发给上游的单笔桌宠关闭有已知边界，见[已知问题 12](#已知问题)（`src/core/home-binding.ts:3–6`、`6dd3e4c:docs/plans/stage3-presentation.md:205–211,226`）。
- **第一轮。** `1e425cf` 给生活世界通知及区内工作带上原代次，`1cb7390`、`e91ec7c` 守住 Room 换绑与写前取消，`0394ec3` 让 Body 计时器沿用原绑定。`ed6fb4f`、`d29438f` 把同一思路接到 Channels 和 Desktop 刷新。这轮主要覆盖状态刷新和 Room 入口。排队中的渠道请求与送达、Room 原生恢复及语音提供方准入、钱包等待登记、桌宠逐笔关闭和 Core 初始化还各有自己的异步边界（`tests/behavior-list/presentation-r7.test.mjs:186–234`、`6dd3e4c:docs/plans/stage3-presentation.md:205–211`）。
- **第二轮。** 审查发现入口或回包校验之间仍可换绑。旧调用经过队列、外部查询、提供方准入或 SQLite 等待，可能重新取到新 A，或在拒绝回包前已经产生效果。`406ed1b` 把比较提到 Core。`6fb06e3` 把渠道原代次贯穿请求、适配器和送达，`b08195a` 把钱包校验推进到登记等待与持久写前，`f08e5f1` 补 Room 原生取消、恢复落盘和语音提供方准入，`f418eec` 在逐笔关闭前后复核，`6ad9e8f` 补 Core 自述落盘与初始化等待结束后的复核（`6dd3e4c:docs/plans/stage3-presentation.md:205–211,247–254`）。共用比较解决字段口径，各入口仍需在能产生效果的地方实际调用它。
- **目前的防线。** `sameHomeBinding` 比较 `workspaceId`、`path`、`storageId`、`bootId` 和 `generation`（`src/core/home-binding.ts:3–6`）。行为清单覆盖旧渠道通知、Room 会话恢复及取消、语音提供方零调用、旧钱包写入和恢复入口拒绝（`tests/behavior-list/index.json:1787–1860`）；桌宠与 Core 的回归及由红转绿记录见 `6dd3e4c:docs/plans/stage3-presentation.md:210–211,234`。
- **同类改动的检查点。** 在入口且首次等待前捕获绑定和生命周期，沿调用链传给下游。逐一标出等待、排队、提供方准入、实际写入、逐笔派发、通知及回包的位置，在恢复执行与产生副作用前复核。验收要卡住其中一个真实等待点，做 A→B→A 并保持可复用标识相同，核对旧请求无新增写入、送达或成功回包，新请求仍能完成；已有提交用原号查证。再次失守时沿这条调用链复盘后再做第 3 批修复。
