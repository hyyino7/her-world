# Her World

这里只写产品现在的样子和阶段规划，历史交给 git。结构见 [architecture.md](architecture.md)，拍板过的取舍见 [decisions.md](decisions.md)。

## 给谁用

- 主人自己：Her World 的所有者和唯一使用者。
- 其次是读代码、维护它的 Claude 和 Codex。

## 核心场景

Her World 是跑在 DSH 里的伙伴插件，同一个伙伴的身份、记忆和生活贯穿各个入口：

1. 在 DSH 原生聊天里和伙伴说话，她记得以前聊过的事。
2. 桌宠（Desktop）和 Room 里能看到她在做什么、心情怎样，也能在那里和她聊天。
3. 她有自己的生活：身体状态、照料、种地、钱包背包、阅读、计划、回顾和日记。
4. 通过 QQ、微信等渠道和语音找到她。
5. 在 DSH 的插件详情页一键更新。

## 解决什么问题

这次重构前，模块边界有三处典型问题。

- Core 反向引用上层模块（桌宠外观、Life 偏好、情绪文件、记忆目录）。
- Life、Behavior、Economy 互相缠绕，实际是同一件事却被切开。
- Room 直接拿 Desktop 的模块，控制台什么都认识。

改一处牵一片，促成了这次**整体重构**，范围见[阶段 1 缩小决定](decisions.md#2026-11-18-阶段-1-缩小m3-改为收口并发版)，职责和依赖边界见[三层架构](architecture.md#0-一页总览)。

**一句话 MVP**：立起三层边界和自动依赖检查，第一层改用登记口（来源适配、能力状态、工具声明），跑通「备份 → 迁移 → 可回滚」；从 0.1.8 升级到新版后，聊天和记忆照常可用，从旧测试里拆出的行为清单逐条通过。

## 不做什么

以下是三层重构的范围。大模型使用细则另见[下一阶段](#下一阶段)。

- 重构期间保持原有功能和玩法，新需求按范围冻结处理。
- 不换掉 DSH 的插件体系，不改 DSH 本身。
- 不拆成多个 npm 包（留到边界稳定之后）。
- 不改 npm 包名 `her-world` 和插件的 bundle ID，保证 DSH 里的更新按钮照常可用。
- 包的对外入口、Cordis 服务名、配置项也保持稳定；确需改动的单独找主人拍板，并在已安装环境里验证升级路径。完整清单见 [architecture.md](architecture.md) 6.1。

## 重构的成功标准

- 改一个功能不再牵一片：比如调种地规则，只动「生活世界」。
- 看一页架构图就能读懂各块职责。
- Room、Channels 等外围模块能整个关掉，不影响聊天和记忆。

## 重构的风险

1. 重写时丢掉旧的特殊情况（种地时钟、去重、日记恢复等）。修复批次的口径和证据见[故障家族](#故障家族)；对策是行为清单。
2. 数据迁移出错，影响唯一的真实数据。对策：迁移与回退演练，见 [architecture.md](architecture.md) 第 7 节。
3. 「生活世界」内的职责容易交缠。三区的归属和调用边界见[架构 2.3](architecture.md#23-第二层生活世界管什么)。
4. 战线长：重写期间，旧版仍要修 bug。对策：见「旧版修 bug 的规则」。
5. 回退受限：现有恢复器要求安装包文件指纹完全一致，只覆盖指定目录；新版运行期间新增的聊天不会自动合并回旧记忆库。
6. DSH 自身升级可能改变插件机制，影响新骨架。本计划假设重构期间 DSH 的插件接口基本稳定，需要持续关注。

## 待验证的假设

- 三层切分在代码里成立：合并后，Room、Desktop 能只靠 contracts 读生活世界的状态。
- 阶段 3 收尾时 `tests/` 有 186 个自动测试入口（59 个 `*.test.ts`、127 个 `*.test.mjs`，编译产物只计一次）。入口按 `scripts/checks/verify.mjs:13–17` 的收集规则盘点，详见体检第 2 节。逐条改用公开边界时，仍须核对原行为断言是否保留。
- 不改包名和 bundle ID，已安装的环境能无缝升级到新版；关闭外围模块不影响聊天和记忆（目前只有源码上的依据，需要在隔离的已安装环境里用真实数据副本演练）。
- 全部真实数据（含浏览器里的经济待确认请求）能完整迁移并回滚（需要停写后的真实副本清单和演练）。
- 重写后维护成本真的降低（用「典型修改前后对比」衡量）。

## 重构的度量与机制

**怎么用这一节：**

- **不估时间。** 每个阶段靠完成标准和停止条件管，不靠日期。
- **每个阶段结束都做三件事**：跑行为清单和门禁，全绿才算完成，并至少走通一条从真实入口开始的完整流程（G9）；更新「典型修改前后对比」；主人验收体验，决定继续、调整还是停下。
- **每个阶段里的具体任务**按大改单独写方案：Claude 写、Codex 挑刺，写进 `docs/plans/`，主人同意后才交给 Codex 实现。
- **先搬后改。** 一个步骤要么只搬家（行为不变，行为清单全绿），要么只改逻辑，不在同一步里同时做。
- **发版粒度**：一个版本只装一个能独立验收、发布和回退的交付单位。

### 行为清单

从旧测试里拆出的「必须保住的行为」。索引在 [tests/behavior-list/index.json](../tests/behavior-list/index.json)，测试及公共夹具在 `tests/behavior-list/`，新用例的源码适配入口集中在 `entries.ts`；索引也复用部分原测试。构建前提、清单命令及直接运行入口见 [开发说明](development.md#architecture-behavior)。

- **L1 完整流程**：插件入口加假原生宿主和假模型，覆盖准入、工具限制、执行、落盘、查询或召回及重启恢复。
- **L2 公开面行为**：经公开服务、原生事件和磁盘边界驱动，不构造内部类、不替换私有方法、不读取私有状态。
- **L3 回归参考**：保留在全量门禁，不算清单完成项，也不由清单运行器执行。

阶段 3 收尾时索引有 173 项，分为 L1 64 项、L2 106 项、L3 3 项，清单执行前两级的 170 项（`tests/behavior-list/index.json:2–8`、`scripts/checks/run-behavior-list.mjs:39–43`）。条目的特殊情况、故障家族和会话策略覆盖也登记在索引里。每类补足 L1 的计划阶段见索引的 `l1Stage`，M1 的完成线是每类至少一条 L1 或 L2、每个故障家族一条 L1。

调研列出的 15 类特殊情况，各有对应的旧测试：计划续行、同请求重试不重复生效、效果已落盘后结算失败再重启（`tests/life/life-domain-integration.test.ts`，混合文件，保留行为断言、换掉故障注入的做法）、睡眠中投喂的终态、种地时钟不倒退、离线消耗额度、日记按原日期恢复、历史日记保护、输入持久化先于确认、送达与记忆召回分开、阅读必须有真实文本、QQ 收件恢复、换目录时在途请求不写旧目录、隐藏后取消显示定时器、缺库不得空白替代。

规则：

- 清单在旧代码上必须**全绿**，才能作为新版的验收。
- 新版每个阶段结束，与该阶段相关的条目必须全绿；**整份清单在阶段 4 结束时全绿**。
- 条目只能增加或修订（要说明理由），不能为了通过而删除。
- 每一类至少有一条**从真实入口走完整条流程**的用例（入口 → 准入 → 工具限制 → 执行 → 落盘 → 查询或召回 → 重启恢复）。例如：自主回顾能写日记、主人聊天补写历史日记也能写；计划步骤完成后自动续下一步；互动送达后在另一个会话里能召回；关闭后晚到的录音不再生效。
- 旧测试待重新分类，B 批的 L1/L2/L3 分级是新的分类；行为断言随对应阶段逐步拆出，阶段 1 先守住上述 M1 完成线。
- 验收按索引里的行为及层次判断，不按文件个数替代。

### Room 空间重做的度量

空间重做阶段 0 对旧版取基线。用默认房子、总览镜头和 `balanced` 画质，分别用 2D 和模型角色模式测三次：空闲 60 秒、走一条跨三个房间的路线、隐藏窗口 5 分钟。记录帧耗时中位数和 95 分位、CPU、GPU、内存、打开到首帧的等待及隐藏耗电。按基线波动在[阶段 0 评审](#room-extension-phase-0)确认容差，导航、躺椅编辑和阶段 2 每批用同一场景对比。编辑另记一次校验和重建的耗时。

沿用[典型修改前后对比](#典型修改前后对比)记录「新增一种复用已有活动的家具」在旧版要改几处。阶段 2 结束时按[扩展路径](architecture.md#room-extension-content)试做同一类家具，目标是三处手写改动，不含测试。

### 「要不要重写」的判断尺度

一个模块出现下面任一条时才重写，否则整体搬进新骨架、不改内容：

- **满足不了依赖规则**：R1–R4 对它报违规，且只靠挪文件、改 import 解决不了。
- **无法单独理解、单独测试**：其测试必须启动其他模块的真实实现才能跑；或手写文件（不含生成文件）超过 **1500 行**时，必须先评估拆分。超过此阈值的手写文件由 `pnpm run metrics` 报告。

### 防止越做越乱的机制

混乱主要来自「范围扩大后拥有者和验收没有跟着收口」和「局部修好、检查通过，又继续叠下一批」。下面这些机制把「变乱」变成能被马上发现、能被叫停的事。

| 编号 | 机制 | 做法 | 落点 |
| --- | --- | --- | --- |
| G1 | **违规棘轮（永久门禁）** | 见 [architecture.md](architecture.md) 第 3 节的「棘轮」 | M1 建立，进入门禁，之后一直生效 |
| G2 | **方案准入问题** | 每份方案加一节「概念与扩展检查」：新增或修改了哪些概念？拥有者是谁？有没有新增词表？复用了哪些已有声明？层间接口有没有变化？**为什么需要这个新职责，对应哪个已确认的用户场景？** 扩大范围的方案还要写清：新增目标替换或延期了什么，当前闭环怎么验收，原完成标准是否作废。审查时对照这一节，并用 R8 报告核对 | M1 起所有方案 |
| G3 | **故障家族复盘** | 按业务流程或不变量归组（不按目录：日记链路横跨 Core、Life 和上游库），计修复批次（同一个提交里的多轮返工也算）。同一个不变量第二次失守就提前复盘；第 3 批相关修复前必须复盘（共同根因、受影响的其他入口、哪条完整流程验证能结束这一轮）。14 天只作报表窗口，不是重新计数的豁免。阈值没有历史校准依据，暂定 | 每个阶段 |
| G4 | **范围冻结** | 阶段内的新想法一律进 `ideas/inbox.md`，不插队；每个阶段只做完成标准里写的事；新增功能须单独立项，或进入下一阶段的完成标准，由主人拍板，并按 G2 重定阶段和验收 | 全程 |
| G5 | **自动度量** | 统计各规则的违规数、词表重复关系和裸字段、`kind`／`action` 判断、超过 1500 行的手写文件和模块间依赖数。阶段收尾和发版前查看报告 | `pnpm run metrics`，只报告 |
| G6 | **`AGENTS.md` 一页入口** | 一页：三层架构图、概念表、「新增东西去哪里登记」。控制在 10 KB 以内（暂定），内容链接到 [architecture.md](architecture.md) 和 `layers.json`，不手抄 | M1 |
| G7 | **规则要有案例** | 每条检查和规则写明对应的真实案例，对应不上的不加 | 全程 |
| G8 | **阶段末复盘规则** | 只有保护目标已经消失、已被更可靠的检查替代、或持续误报且没有有效案例时，才删除或放宽。「整个阶段零报警」不是删除理由 | 每个阶段 |
| G9 | **完成标准含真实流程** | 每个阶段的完成标准至少包含一条从真实入口走完整条流程的验证。每个模块自己的测试各自通过，不能代替这条。反复出现的缺口都是这一类：自主回顾能写日记，主人聊天补写却被另一层守卫拒绝；计划步骤完成后不自动续下一步；互动已送达，在另一个会话里却召回不到 | 每个阶段 |

**必须 / 可后置**：必须的是 G1、G2、G3、G9，以及行为清单、迁移演练和里程碑评审点；可后置的是 G6；G5 由命令输出。

**这些机制抓不住、要靠人判断的**：初始范围本身就过宽，或需求本身不必要（G2 里「对应哪个用户场景」是唯一的防线）；合法接口内部的行为错误（靠 G9 和行为清单）。

### 旧版修 bug 的规则

- 先把会失败的测试写进行为清单，再修在当前主线。
- 修的如果是正被替换的模块，修复和测试一起并入新实现，不在旧、新两处各修一次；该替换单位的完成标准里核对这条测试通过。
- 只修 bug，不顺手加功能（G4）；同一分支同一时间只有一个 Agent 写。
- 同一个 bug 反复在不同入口出现，按 G3 处理。

### 故障家族

**修复批次如何数：** 一个不变量的一轮修复记一批（F）；一个提交里的不同不变量或有证据的再次返工分别记，附随测试、生成基线、结果文档和合并不重复记。功能（N）、发版（P）、其他（O）同样按交付批次去重。分类依据是提交说明、源码/测试差异和保存的执行结果，拿不准的已标估计；没有记录的轮次不补猜。

**阶段 3 修复批次占比估计为 14 / 23（60.9%）。** 分母包括 7 个实施批、2 次发布和 14 个可辨认修复轮次（体检第 7 节）。实施中 6 轮是 Compact 取消、Room 写前取消、绑定代次首轮、桌宠投喂、Console 路由撤销／重复登记和钱包旧页竞写及停写。审查返工 7 轮是绑定代次、回包与实际效果、钱包离线同轮证据、身体呈现、计划读取失败仍停自治、Room 开窗隔离和 Compact 语音取消（`6dd3e4c:docs/plans/stage3-presentation.md:205–232`）。发布后钱包声明路线解决生产迁移阻断，再计 1 轮（`ebf53f1`）。合并历史里未保留的轮次待核实。

#### 行为规则与极端情况

| 规则 | 拟交付的行为 |
| --- | --- |
| 追加与清理 | 历史按会话身份选择策略。适用会话平时只追加，允许改写的四类时刻是压缩（含 DSH 工具结果裁剪、图片卸载）、轮换、撤回和失效。压缩或轮换清旧召回、快照和可瘦身工具结果，相邻的边界信号合并清一次。记忆关闭、解绑、故障或换工作区时清旧召回，聊天继续，迟到的召回或决策结果丢弃。首次安装无资料时，召回和增量为空。 |
| 自动与主动召回 | 压缩、轮换、新会话首轮或记忆服务恢复后的第一轮做完整召回。平时仍按本轮输入查询，按记忆 ID 和版本只追加新条目，旧版本留到边界。她仍可主动查记忆。长期少压缩导致输入增长时，按[大模型使用 1c](#大模型使用-1c-主人会话只在四类时刻改写)的成本和连贯性试验决定能否发布。 |
| 撤回 | 下一次准备请求时立即清自动召回及主动召回结果中的对应条目，覆盖并行工具晚返回、轮内后续步骤和重试。已经发出的请求无法追回。升级前没有条目列表的召回在首次撤回时整段清；主动结果只删目标条目，全删时保留工具配对并显示已撤回。旧回复转述、DSH 摘要和检查点按主人接受的范围保留，撤回前或同时开始的压缩也可能保留旧材料，压缩后的第一次请求再清。 |
| 设定与自我认知 | 主人修改设定立即生效，接受由此产生的一次未命中。她编辑自我认知仍立即生效，边界发布与轮换一起后置。 |
| 生活状态和动作 | 每个会话按自己的读位置追加，压缩后先补完整现状再续读。同一记录可在压缩前后各呈现一次。 |
| 主人接管与续跑 | 经核验、实际准入到主人会话的输入直接处理，计算闲置时用最后一次准入时间。主人群聊走 guest，独立 Desktop、Room 和准入失败的发送均不算本次接管。生活做完当前一步再停，暂停期间不启动新生活回合。在途身体操作、结算、回执核对照常完成。身体命令仍由 Body 按到达顺序串行处理。跨日先按原 `reviewDay` 补回顾，再按新一天计划行动，已过期的计划按现行规则回报。预算提醒归生活会话，停着时只在设置页显示。 |
| 三级触发 | 规则先判，判不了才以轻量模型和最低推理强度做一次不留历史的决策，决定要回才申请进入完整会话。生活会话运行时外界信号排队。群消息按静默窗口合批，持续来信到最长等待也处理。决策超时或格式错误时，@ 和私聊按「要回」交现有准入，其余记原因并结束。 |
| 决策、准入与回执 | 决策结果先持久化再行动，分开记已决策、已准入、回复已生成、已投递。落盘前崩溃可重算一次，落盘后续做。投递后未存回执按原消息核对，无法确认则标「待核对」，不重投。 |
| 用量与缺报 | 按调用结束时刻及生活时区归日，价格按开始时刻对应的价表版本和时段。换模型分别记，未知模型显示「无价格」，缺缓存字段记「未报」。磁盘满或文件损坏时聊天继续，用量页显示记录失败次数，提示合计覆盖范围。 |
| 人称 | 「我」指她自己。设定、自我认知、日记、记忆和状态采用她的叙述视角；别人用固定称呼，主人全程同一称呼。保留引文原话并标明谁说的，和她自己的判断分开。 |

#### 发版与实施顺序

账本和用量页、统计切换各发一版。主人会话只追加、生活增量、拆生活会话、决策服务及可选轮换各发一版。收件箱依次发行读取端和写入端，QQ 过线才接微信。观测只交付脚本和基线，恢复补批单独排期。每个发行单位在隔离的已装环境走自己的入口流程，分别验升级、降级和恢复。旧行为的缺陷按现有修复规则处理，落在当前单位改动范围内的写进该方案。

MVP 是补全入口用量、量出基线，并交付主人会话平时只追加与有效撤回。大模型使用 1a 期间可准备观测脚本、合成序列和评分表；大模型使用 2a 的全段清单和合成用例可在大模型使用 1c 并行准备，开始大模型使用 2a 前交付。大模型使用 2a 起的完成标准在大模型使用 1b 后按实测修订。[各单位的止步状态](#各单位的止步状态)决定哪些结果可独立交付。

| **大模型使用 1a-1** 加[用量账本和归因](architecture.md#llm-storage-plan)及用量页 | 「用量全覆盖」「账本不含内容」检查通过；和旧统计并行跑，旧统计覆盖的部分（home 的 `assistant/message`、渠道核验过的输入）按旧口径对得上，差异逐条说明来源；账本写失败时聊天照常（故意让账本目录只读验证） | 在隔离安装里用合成资料：DSH 原生聊天、QQ 主人私聊、桌面、Room 各聊一句，guest 私聊一句，跑一个 Life 回合和一次回顾，触发一次碎碎念和一次压缩 → 用量页里每类都有，归类正确，命中和未命中分开 → 退出 DSH 再开，记录还在 |
| **大模型使用 1a-2** 渠道统计和 Life 预算改成从账本派生 | 「账本和旧统计一致」检查通过；Her World 整份行为清单通过 | 同上流程跑一遍，设置页的预算与渠道用量按可比口径对得上；缺报和新定价规则带来的差异已说明 |

某类调用两轮都归不了类时，保留「未归类」并报警，以 DSH 插件缺会话 ID 和用途为例。账本和旧统计两轮对不上时停在并行记账，先查差异来自哪一边，再判断能否发统计切换版。

#### 大模型使用 1b 观测和基线

| 做什么 | 完成标准 |
| --- | --- |
| 「请求差异」离线脚本：假模型 + 真实适配器序列化，比较相邻请求的**结构化**内容（消息块、系统提示词、工具声明，不比原始字节，因为适配器会合并相邻同角色内容、合入扩展字段），分别开关召回替换、状态退休、瘦身、Life 换工具、重开请求系列 | 一份差异报告：每种改写让差异从哪里开始、频率多高。离线只做定位，不推算 token |
| 合成对话序列：一组主人会话的多轮对话，中间夹 Life 回合、回顾、一次撤回（她用 `pet_memory_forget`）、一次压缩；固定 DSH 版本、路由、模型实际版本、推理强度、请求间隔、冷热启动方式、失败重试口径 | 序列和跑法入库，可以重复跑，之后大模型使用 1c、大模型使用 2a、大模型使用 2b 都用它对比 |
| 付费 A/B：合成序列在真实模型上，分别关掉召回替换、状态退休、瘦身、Life 换工具中的一项，各跑三遍 | 每种改写各占多少未命中输入；三遍的波动用来定大模型使用 1c 的容差 |
| 连贯性抽查固定 10 个问题，覆盖「刚才在干嘛」「为什么去做」「前一天聊过的事」「撤回的事别再提」，每题 0–2 分 | 在改动前的版本上答一遍，主人给合成回答打分，结果记在本文 |
| 真实用量（检查点） | 大模型使用 1a 发版后主人正常用一周，自己在用量页看各入口的花费和命中比例。Agent 不读这些数字；主人只回传评审结论（A / B / C）和「真实用量的趋势和合成序列是否一致」 |

从已装环境的 QQ 主人私聊入口跑合成序列，再由同一捕获点对照基线和分项开关。量不清归因、改写代价或连贯性时停在可复跑的观测，按下方 C 路评审。

##### 大模型使用 1b 评审

评审时与主人核对差异报告、付费 A/B 的成本拆分、连贯性基线和主人确认的真实使用趋势。这里的 A、B、C 决定实施顺序，与已选定的段声明方案 A 分别记录。

- **A 先做大模型使用 1c**。召回和投影改写值得优化，且账本和接点能撑起验证时，按[已拍板的声明范围](architecture.md#llm-segment-plan)实施大模型使用 1c。一起定大模型使用 1c 的目标数字，候选为合成序列未命中输入下降 30%，总成本要下降，连贯性抽查每题不低于基线，同时满足[成本、连贯性和撤回验收](#llm-product-acceptance)。
- **B 先做大模型使用 2a、大模型使用 2b**。若 Life 工具切换和回合是主要代价，先用大模型使用 2a 的生活增量和人称组装保住连贯，再拆大模型使用 2b。大模型使用 2a 自己处理增量读位置和边界快照，其他投影照当前做法。大模型使用 2b 先沿用当前召回与投影，实测拆分后的基线；再按新基线做大模型使用 1c，对主人及生活两条会话验只追加。MVP 完成点仍在大模型使用 1c。
- **C 止步或缩小**。若改写成本小、证据不足或接点无法安全验证，可以收在账本与观测。主人可另批只做大模型使用 2a 的连贯性和人称改进，按该单位的标准验收。MVP 的节省和撤回仍待大模型使用 1c 完成。

#### 大模型使用 1c 主人会话只在四类时刻改写

- 交付按[受管段声明](architecture.md#llm-segment-plan)执行的只追加与清理。沿用 `startsRequestSeries:true`（见[现行请求接点](architecture.md#llm-request-current)）。若日后单独评估移除，先验证主人 → Life → 回顾 → 接管 → 主人及改提示词、裁剪、重试时，工具声明和执行权限仍一致。
- 完成标准沿用[产品验收](#llm-product-acceptance)。请求断言覆盖轮内后续步骤、并行工具晚返回、压缩前后和重试，按[撤回规则](#llm-product-rules)分别验自动召回、主动召回和原生摘要。除已确认的例外，相邻请求的差异只在末尾。验收过线的范围必须包括该会话当时承载的 Life 和回顾轮次。变更旧「锁做法」测试时逐条保留结果要求，跑全份行为清单，更新 Her World 架构 5.8.4 和 5.9 中实际受影响的规则。
- 隔离流程使用合成资料。QQ 主人私聊约十轮 → 走一个 Life 回合和一次回顾（A 路在同一 home，B 路在拆出的生活会话）→ 请她用 `pet_memory_forget` 忘记刚用过的一条记忆 → 断言下一次模型请求 → 触发压缩后提问 → 重启 → 核对撤回、连续性和账本归类。
- 合成序列两轮达不到目标时，按[召回取舍](decisions.md#llm-usage-decisions)试只在边界召回，并重跑连贯性与撤回检查；仍不达标就止步。撤回可见性两轮修不好时，停在已发布的行为。如果同一不变量再次失守，按 Her World 的故障家族规则复盘。上一个发行版还须在同一 DSH 上实际读回追加日志，离线恢复按[迁移演练](architecture.md#llm-rollback-plan)核查。

**MVP 发版前完成标准**

- [ ] 大模型使用 1a 各类调用入账、归类和并行对账通过，大模型使用 1b 基线可复现，大模型使用 1c 成本达评审目标且连贯性每题不退步。
- [ ] 隔离安装走完大模型使用 1c 流程，重启后撤回生效、账本仍可查。
- [ ] 受管投影的校验、升级、降级和恢复有合成演练证据。旧版读回、恢复到备份时的撤回状态及保留的回执按[迁移与回退](architecture.md#llm-rollback-plan)核对，恢复顺序与保留记录写进发版说明。
- [ ] 走 B 路时，大模型使用 2a、大模型使用 2b 各自过线后，再用拆分后基线验证本 MVP。大模型使用 2a 的独立验收和可选的找回聊天另有止步状态。

发版后由主人反馈真实使用趋势是否与合成序列一致。

#### 大模型使用 2a 生活增量、段声明和人称

- 开始前交付[段清单](architecture.md#llm-segment-plan)，逐段包括人称，标出待定项、重复顺序和保留的事实依赖。按主人同意的声明范围加入检查，使用冲突和越界的合成例子验证检查能拦住问题。处理 `order` 冲突时同时验组内顺序和事实确认。
- 在主人会话、Desktop、Room 走增量投递。核对边界后的快照、重启续读、同一有效历史不漏不重、旧版可读回以及事实确认。按[人称验收](#llm-product-acceptance)核对合成请求及跨入口回答，权限不变。只更新本单位改变的会话策略说明及对应测试。
- 隔离流程使用合成资料。她在家里浇花 → 主人在 Desktop 和 Room 问做了什么、为什么做 → 加入主人原话、群友同形原话和她自己的推断 → 核对称呼和证据归属 → 重启后再问并核对增量。
- 增量连贯性两轮不达标或组装顺序、可见性无法守住时，停在上一个可用版本。确认为动作记录缺缘由时，先评审是否补计划理由。人称没有可复现的歧义时先交付清单，标明人称验收待完成。优先发行可独立验收的增量时，由主人确认缩小范围。

#### 大模型使用 2b 拆出生活会话

| 做什么 | 完成标准 | 真实流程 |
| --- | --- | --- |
| 生活会话身份归生活世界。A 路沿用大模型使用 1c 的只追加；B 路按大模型使用 1b 评审约定先用当前投影。Life、回顾、预算提醒改投生活会话；主人开口时生活回合做完当前这一步就停，主人会话闲置一段时间后恢复（候选 10 分钟，从主人会话最后一次准入的输入算起，和 QQ 的回复超时不是同一个时钟）；`ownerHome` 和桥接保留原主人会话；按各自身份调整主动联络、回顾压缩、设置页和送达归属；迁移按主人显式触发、停写后做 | 「主人接管」检查通过；迁移、降级、恢复、迁移中途崩溃续做在合成副本上通过，每种写清生活会话、在途投递和预算记录的去向；真实副本检查点通过；主人消息到第一个字的等待不比拆分前长（起止点：主人会话准入输入 → 第一个可见字；QQ 另量从输入准入到整条回复送达；容差用大模型使用 1b 的方法量波动后定）；A 路验证主人会话未命中输入相对大模型使用 1c 继续下降，B 路重测拆分后基线；Her World 整份行为清单通过 | [核心场景](#llm-product-acceptance)中，生活会话写回顾时主人 QQ 私聊打断 → 回复送回原私聊 → 闲置后回顾按原日期补写完 → 计划、日记、结算核对 → 设置页归类正确 |

停止条件：迁移演练两轮失败：不发版；主人接管后计划、回顾或结算两轮卡住：停下来，重新评审[主人接管规则](#llm-product-rules)。

#### 大模型使用 3a 决策调用服务

交付[独立决策调用服务](architecture.md#llm-session-plan)，先用于规则判断不了的生活计划信号。「决策调用」的服务检查通过后，在 Life 入口用合成信号走通「规则 → 决策 → 生活回合」。同一组合成生活信号中，每个有效回应的总成本须低于引入服务前，生活行为保持原有验收标准。

成本或生活行为未过线时停在原触发方式，暂不启用决策调用。

#### 大模型使用 3b 收件箱接决策

QQ 收件箱加决策状态，按 owner / guest 分开；guest 会话改成只追加；先在 QQ 上走通崩溃恢复和回退，再接用另一套收据的微信。合并规则：静默窗口复用[QQ 的 `batchQuietMs`](architecture.md#llm-channel-current)，最长等待候选 60 秒，被 @ 和私聊优先；用持续来信、@ 和私聊并发、队列饱和三种合成流量验证。先发读取端版本；放行写入端的证据是演练「写入端已写下新状态 → 降回读取端 → 重启 → 再升级」，状态和回执核对无误，不按固定天数。完成标准：「决策调用」「收件箱新旧版本」检查通过；同样的合成群聊流量，「每个有效回应的总成本」比大模型使用 3a 前低；在现有准入规则允许的范围内被 @、私聊的消息一条不漏；真实流程：一个测试群里连续发二十条消息，中间 @ 她一次 → 她只回 @ 的那条和值得回的 → 设置页里群聊的决策调用和完整会话分开计。

停止条件：决策判断错的比例在合成样本里两轮降不下来（阈值在大模型使用 3b 方案里定）：停下，回到「规则 + 完整会话」两级。

#### 大模型使用 4 主人会话轮换（可后置）

只有在账本显示主人会话持续变长、压缩控制不住时才做：每日回顾后闲置够久就轮换，带交接摘要；自我认知在轮换和压缩时写进前缀。开工前单独立方案。完成标准草案：真实流程「回顾完成 → 闲置到点 → 轮换 → 主人在 QQ 问前一天聊过的事，答得上 → 设置页看到旧会话已归档」；连贯性抽查不低于轮换前。停止条件：交接摘要两轮都丢掉主人在意的事，停下，回到只靠压缩。

#### 大模型使用可选恢复补批

把「找回新版期间聊天」安排在大模型使用 2b 的回退演练已经通过后，单独评审和演练。以[迁移与回退](architecture.md#llm-rollback-plan)的恢复前安全备份为输入，用合成旧会话追加新聊天和新版新会话，离线恢复后再核对哪些记录可以安全找回。成功标准见[产品验收](#llm-product-acceptance)。找回路径或去重验不清时，保留安全备份和现有恢复结果，本补批止步。

#### 机制清单

每条新机制写明依据类型：**现有约束**（已有规则或代码协议，不守就会坏）、**事故**（出过的问题）、**决定**（简述或拍板定下的取舍）。对应不上的不加。每条新检查建立时，用一份故意违规的样例证明它拦得住。

| 机制 | 必须 / 可后置 | 依据 | 依据类型 | 建立阶段 |

| 用量账本和「用量全覆盖」 | 必须 | [旧用量统计及覆盖](architecture.md#llm-usage-current) | 现有约束 | 大模型使用 1a |

| 决策调用的幂等和失败处理 | 必须 | [QQ 收件与核对](architecture.md#llm-channel-current)要求保住旧输入和待核对状态 | 现有约束 | 大模型使用 3a、大模型使用 3b |

| 每个有效回应的总成本 | 必须 | 同一信号可能产生额外的决策调用 | 决定 | 大模型使用 3a、大模型使用 3b |
| 每日总上限 | 可后置 | 先建立可比较的用量，再据账本决定是否需要硬拦调用 | 决定 | 不排期 |
| 主人会话轮换 | 可后置 | [轮换决定](decisions.md#llm-usage-decisions) | 决定 | 大模型使用 4 |

#### 真实数据与付费授权

开发、演练和入口验收使用隔离安装及合成资料。主人自己查看大模型使用 1b 的真实用量检查点，按该单位的口径回传结论。大模型使用 2b 的迁移检查由主人提供停写后的隔离副本，受控程序只输出路径、会话 ID 是否存在、条数和通过与否。人称错乱和恢复补批只用合成资料。[恢复入口与边界](architecture.md#72-回退)

大模型使用 1a 开工前，由主人确认用于验收的账户、各单位与总额度、重试上限和授权人，超额即停。真实模型只用于获准的隔离验收、付费对照及对应演练，单元和集成测试一律用假模型。

### 空间重做与内容扩展

主人能在 Room 里摆家具，保存后重开仍能看到同一布局，她能按新布局走过去使用。之后按阶段开放房屋装修、新地区和玩法。维护者按[空间内容的扩展路径](architecture.md#room-extension-content)添加内容。首个交付闭环只开放阳台躺椅在阳台内平移，沿用现有外观。

目前场景几何和站位随包发布，Room 共享传输表没有布局读写入口（`vendor/feiyu-room-template/public/room/world.js:1539–1557`、`vendor/feiyu-room-template/home-state.js:76–80`、`src/presentation/room-transport.ts:8–18`）。立项取舍及两组大改的优先级见[立项与选型决定](decisions.md#room-extension-decisions)。

<a id="room-extension-acceptance"></a>

#### 核心场景与验收

| 主人要做的事 | 达成标准 |
| --- | --- |
| 挪躺椅，让她走过去坐下 | 拖动躺椅并保存 → 她下次选用躺椅时按新路线走去 → 实际到达后坐下，热点也跟着走 → 退出 DSH 再开，布局和身体状态正确，家里其他交互点仍可到达。 |
| 知道为什么挪不了 | 越界、重叠、压到她或她的路线、堵住门或让其他站位不可达，都提示原因并恢复到已保存位置。她正在使用、走向或计划仍引用该家具时，首版拒绝挪动。 |
| 升级后照常看她生活 | 升级前保留的走路、停留、睡眠、暂停计划和园艺任务按原期限和回执继续。照料、种地、聊天、投屏、拍照等按[既有行为与待补用例](architecture.md#room-extension-behavior)逐项验。 |
| 看到后续的新内容能用 | 分批实走挪家具、从新门走过、和她下棋中途重开、外部内容来源准入及模型离线时的确定性作息。各批入口和停止条件见下文。 |

**有意改变**。自动导航按房屋结构和家具占地算路，保留室内外通行和现有交互点的进出。路线形状、走路耗时可改变，后续活动按实际到达开始，原截止时间照常生效。不可达时她停在原处，步骤失败，计划转为等待且不反复重试；只有已经在使用位并正使用该点才可直接停留。阶段 2 的电视、书桌屏幕与陪看镜头随家具走。[导航接点与验收](architecture.md#room-extension-navigation)

**不做什么**。不改 DSH，无通用生活插件系统，家具种类由维护者随包提供，主人不能上传自制模型。菜畦、种子工作台、收成台、堆肥箱、记忆板固定，菜畦编号、作物和已有任务保留。首版范围排除家具旋转、购买和经济挂钩、多人摆放、跨地区移动、撤销历史和文生 3D。换模型、改房屋结构、新地区、玩法和外部内容家具从阶段 2 起分期交付。

#### 特殊情况

| 情况 | 处理 |
| --- | --- |
| 首次安装或旧存档升级 | 显式初始化才为新绑定建默认布局；旧存档按[布局迁移](architecture.md#room-extension-migration)保住在途状态。 |
| 布局损坏或比当前代码新 | 保留原档并提示「待核对」，暂停依赖布局的活动和拍照，避免反复失败或唤醒模型。时间推进、已提交的结算照常。 |
| 拖到一半取消、松手后关窗或切工作区 | 松手前取消不保存。已提交但未收到结果时视为待确认，重开以最新已保存布局为准。旧工作区请求不能写进新绑定；隐藏或锁屏期间生活继续，已停止的投屏须重新选画面。 |
| 两笔编辑竞争，或提交时她刚到达、开始照料 | 按最新身体状态重新校验，版本冲突时显示最新保存位置；同一请求重试返回原结果。首版保持在途路线可用，详细规则见[布局写入协议](architecture.md#room-extension-storage)。 |
| 拖动她落在家具上、挪动导致走不到或超过计划截止 | 拖她仍直接落点，下一次走路先脱困；家具编辑按角色宽度验通行，平铺地毯可通行。到不了或赶不上时如实回报，沿用原截止规则。 |
| 换回旧版 | 发版说明告知本批能否只换包，以及离线恢复对布局、聊天和其余存档的影响。[换包与恢复边界](architecture.md#room-extension-migration) |

#### 发版与实施顺序

先安排[大模型使用细则的 MVP 链](decisions.md#room-extension-priority)。空间重做阶段 0 可并行准备独立的原型、合成样本及用例；阶段 1 开工前按届时的发行基线重跑。1a、1b、1c 在 Room、Body、Plan 的接点避开大模型使用 2a、2b、3a 的同处修改；1e 在 Channels 的接点与大模型使用 3b 错开。采用现有获准来源的家具可按阶段 4 排期，需要收件箱参与决策的等大模型使用 3b 对应渠道读写端验收。

各单位单独写方案并经主人批准，按[度量与机制](#重构的度量与机制)发版。空间结构按先搬后改推进，到 1c 发版结束，1d 起逐项交付功能。新旧 Room 不并行，自动导航发布时移除旧路线图。结构重做期间的缺陷按[旧版修 bug 的规则](#旧版修-bug-的规则)处理。各版在隔离的已装环境实走本批入口，核对旧行为、升级和回退。阶段 2–5 的完成标准在阶段 1 验收后按实测细化。

<a id="room-extension-phase-0"></a>

#### 阶段 0 安全网

沿用[行为清单](#行为清单)的分级和验收方式，把 Room [缺失的断言](architecture.md#room-extension-behavior)补到可复用入口，接管前在旧实现跑通。实走点地走到后重开、计划收到到达回执后续行，以及选屏、看画面和面板、停投、换屏、隐藏后重选。取[性能和扩展处数基线](#room-空间重做的度量)，准备合成存档、迁移骨架与[三类演练](architecture.md#room-extension-migration)，完成[导航原型对比](architecture.md#room-extension-navigation)。本阶段不发版。

阶段 0 盘点和 1b 发版前迁移验收是两个真实数据检查点。由主人提供停写后的隔离副本，受控程序只输出路径、字段名、版本、条数和通过与否。开发、测试与演练使用合成存档和假模型，需真实模型的隔离验收与演练先按[授权决定](decisions.md#room-extension-open-decisions)确认。

阶段 1 开始前，主人按行为通过情况、不可测项、旧格式盘点、导航结果、性能容差和各单位工作量评审。旧行为两轮仍测不稳就列为不可测；发现清单外的旧格式先补清单；两种导航原型都过不了关键场景就带结果评审。

- **A 继续**。确认导航实现，按规划推进阶段 1–4，阶段 5 按依赖验收。
- **B 缩小**。只做阶段 1，保留手写外观。两种原型均不通过时，可缩到接管与交互点，继续用旧路线图，暂缓摆家具。
- **C 止步**。保留行为清单、性能基线、合成存档生成器和迁移骨架，Room 继续用现行实现。

#### 阶段 1 挪阳台躺椅（MVP）

1a 完成后，1e 可独立排期，与 1b–1d 无技术依赖。五个单位各自发布，按[换包与恢复规则](architecture.md#room-extension-migration)演练并留存升级前备份至下一版稳定。

| 单位 | 交付与完成标准 | 已装环境验收 |
| --- | --- | --- |
| 1a 接管 Room、Body 和菜园 | 按[分组接管决定](decisions.md#room-extension-decisions)先批准本组；依[代码去向](architecture.md#room-extension-takeover)先搬身体和菜园，再搬页面与资源。两份行为清单、接管检查、交付包和页面注入通过。超过单提交阈值的范围在该单位方案预先声明。 | 打开 Room，点地走到、种一次菜、选屏看画面和面板再停投，退出 DSH 后重开。 |
| 1e 接管 Channels 余项 | 批准本组后搬 Channels，完成[接管收口](architecture.md#room-extension-takeover)。接管检查与 Channels 回归通过。 | 测试群收消息、回复、记录好感和贴纸，重启后检查投递无重复。 |
| 1b 交互点 | 上线空间区和布局存档，迁移静止引用，走路沿用旧路线图。[布局检查](architecture.md#room-extension-checks)和迁移演练通过，含两条身体路径、钱包采用状态、混合引用及真实副本检查点。 | 隔离安装用行走中、含暂停计划的合成存档升级，验证走完、计划续行和再次重启。 |
| 1c 自动导航 | 采用阶段 0 选定的实现。[导航](architecture.md#room-extension-navigation)、行为和性能验收通过；本批按有意改变修订对应测试。 | 依次去沙发、电视位、床、菜园门；途中退出 DSH，重开按原时间规则抵达。 |
| 1d 挪躺椅 | 先在默认布局验单件对象的外观、热点和照片，再接命令、回执与编辑界面。验核心场景、拒绝与并发、重载、存档兼容、性能和升级回退。 | 实走[核心场景](#room-extension-acceptance)中的挪躺椅流程；改完布局重跑可达性。 |

搬家两轮仍守不住旧行为，回到阶段 0 评审。1b 两轮迁移失败则暂停 1c。1c 选定实现两轮过不了导航验收，试对比中的另一种，两种均失败由主人在缩小和止步之间选。1d 的外观、热点或照片两轮对不上，或回执、并发两轮仍不一致，暂停发版。编辑重建超出阈值且一轮优化仍未达标，停下评审编辑时机。

#### 阶段 2 家具编辑与模型

先用一件候选模型在原场景做 2D、模型角色截图，主人确认观感后再换。逐批开放登记家具，支持可验证的途中路线重算；移动电视、书桌要验证屏幕和镜头，移动电视时如何处理在播投屏在该批定。移动床在提交时复核占用，到床才入睡，床头水和唤醒都关联同一床的交互点。

每批实走「挪家具 → 她走过去用 → 重启」，通过行为与性能对比。阶段结束时[资产及外观检查](architecture.md#room-extension-checks)通过，登记家具的手写外观清零，房屋结构、菜园、装饰及程序化 3D 角色不计，完成[加家具的处数试做](#room-空间重做的度量)。样本观感未过则只拆现有家具，性能两轮优化未过就停在上一批，途中重算两轮未过就沿用首版拒绝规则。

#### 阶段 3 装修房屋结构

按门窗、墙、房间划分分别交付。验门窗开洞、家具吸附、导航重建、拒绝堵死房间，以及剖切墙、屋顶、标签、灯光随布局更新。实走移门后她走新门、重开后门仍在。某项两轮仍守不住旧行为，停在已交付项。

#### 阶段 4 新地区、玩法与外部内容家具

按[扩展路径](architecture.md#room-extension-content)分别交付一个新地区、五子棋和一件可看外部内容的家具。新地区实走场景加载和当地交互点；一盘棋验开始、暂停、取消、关窗和重启续局；外部内容验三个授权面分别生效。玩法若需要私有调度或写存储，停下重审。

#### 阶段 5 需求和规则作息

验模型不可用时确定性作息仍走现有活动和回执。「想主动聊天」的阈值先生成生活信号，经[三级触发规则](#llm-product-rules)判断。规则判不了的路径等[大模型使用 3a](#大模型使用-3a-决策调用服务)及 Life 接点过线，验拒绝、超时、取消、换绑定和用量归类；生活回合仍走[既有呈现与送达出口](architecture.md#52-第二层对外)。若依赖渠道收件决策才等[大模型使用 3b](#大模型使用-3b-收件箱接决策)。模型路径未过时保留原触发，确定性规则可单独交付。
