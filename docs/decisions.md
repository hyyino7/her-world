# 关键决定

这里记录仍适用的决定及理由。历史步骤和已取代的条目由版本标签与 Git 保留。

## 2026-11-16 在同一仓库里分三层重做底层，数据全部保留

- 决定：重新划成伙伴本体、生活世界、呈现与连接三层；上层只能通过 contracts 访问下层，由自动检查守住。先立新骨架，再从底层往上一块块重写，写完一块删掉对应的旧代码，每一步都能跑、能发版。代码留在原仓库，按新项目管理（行为清单、迁移与回退演练、分阶段、评审点）。
- 为什么：Core 反向引用上层，Life、Behavior、Economy 互相缠绕，Room 直接拿 Desktop 的模块，改一处牵一片。
- 放弃的选项：
  - 只理顺依赖 — 治标，生活相关三块的缠绕不会消失。
  - 先拆成多个 npm 包 — 边界没理清就拆，是把乱搬进多个包，发布和升级更复杂；留作最后一步。
  - 新仓库从零写 — 要同时养两套代码，切换那天风险集中。
  - 并行新目录最后一次性替换 — 中途发不了版。

## 2026-11-16 没有现成替代，上游代码整体复用

- 决定：`vendor/mnemosyne` 作为记忆引擎整体复用，只重新装配接口、身份范围、创建和关闭；`vendor/dsh-pet`、`vendor/dsh-world`、`vendor/feiyu-room-template` 整体保留，按层分配消费它们的适配器。`client.js`、`shared-core.js` 是生成文件，要改就改生成器。
- 为什么：调研（基线 0.1.8，只读）没有找到必须重写的证据；Project AIRI、Open-LLM-VTuber、Replika 都缺长期记忆或 DSH 接入，或者不能自托管和迁移数据，而重构的前提是保留已有数据和 DSH 体系。
- 放弃的选项：重写记忆引擎 — 没有证据表明需要。

## 生活世界的所有权与首次采用

Body、计划回顾、Economy 共用生活实例并独立装卸。尚未采用 Economy 的菜园由 Body 写在当前身体检查点旁，第一次采用时随建库事务交接。已采用的绑定按采用证据保护原钱包和权威菜园。见[状态拥有者表](architecture.md#4-状态拥有者表)。

## 2026-11-16 控制台、语音和经济待确认请求的定位

- 决定：控制台外观先不动，架构定位现在定：第三层里唯一允许操作别的第三层模块的模块，通过运维操作表操作。语音由第一层 contracts 声明接口，Voice 登记为实现。经济待确认请求存入钱包，凭原号核对、重试或放弃。
- 为什么：同层禁止依赖要和控制台的实际职责不矛盾；能力状态行不能被调用，也没有取消和失效约定；持久待办跨重启后仍可查证。
- 放弃的选项：控制台架构推迟；用能力状态表使用 Voice。

- 为什么：复盘显示，只报告的话，历史上的扩张和协议分散几乎都会照常通过；「用了编译器接口」本身不能证明覆盖率。

## 2026-11-17 架构检查不扫 vendor 里的生成源，R8 条目按位置记身份

- 决定：生成文件不扫描，它们的生成源里只扫生成脚本和 `src/` 里的文件，`vendor/` 里的生成源跳过，由 `check:arch -- --report` 单独列出（收窄拍板点 7）。R8 重复关系的基线身份是「规则 + 双方文件 + 双方函数路径 + 本方形状」，不含集合取值、表达式正文和重复/子集关系。
- 为什么：vendor 是上游代码，扫进来会产生无法处理的词表重复和误报，同步上游时门禁会卡死，而且只减不增的基线没有正当出路；同样，身份里带取值，改一句标签文案或给已有集合加一个值也会被永久挡住。
- 放弃的选项：照原样扫描 vendor 生成源；R8 身份包含取值或关系。

## 2026-11-19 setup 经 DSH 装 npm 包，Core 配置只放 profile 层覆盖

- 决定（已知问题 8）：
  - `dafeiyu-setup --apply` 用 DSH 自带的插件命令安装 npm 上的 `her-world`：默认装稳定版，`--version <版本>` 可以指定。完整的 `00-Core` 配置写进 profile 的 `cordis.patch.yml` 覆盖，读回核对一致后才发布 `installation.json` 回执。
  - 现用 npm profile 可离线运行 `dafeiyu-setup repair-core-config`。默认只核对，加 `--apply` 才补写缺失的安装回执或恢复丢失的 profile Core 覆盖。输出只给状态、路径和固定原因码。
  - profile Core 覆盖丢失时，只有已完成回执与当前包、profile、Core 库和存储绑定交叉核对通过，才允许据此恢复。
  - 半途失败时，脚本只自动回滚能证明安全的 profile 补丁和回执；包或数据状态不明，就保留 `applying` 和快照，交给主人走 DSH 和离线恢复。即使用 `--no-backup` 也保留这两份快照。
  - 测试用和本机 DSH 同版本的 `@deepseek-ai/cordis-plugin-include` 作为开发依赖，跑上游真实的补丁算法；运行时仍用 DSH 应用自带的。
- 为什么：
  - npm 包里的 patch 不带 `config`。配置写在包里，换包就丢；写在 profile 层，不随包变。日常机器本来就是这种形状。
  - 配置、包、数据库各有自己的完成证据，脚本不去猜它们的状态。
  - CI 上没有 DSH 应用，自己模拟补丁算法证明不了换包后真的能解析。
- 放弃的选项：继续从归档重打包、只在文档里写手动覆盖；新增一个单独发布的迁移命令（要改 `package.json` 的 `files`）；在测试里手写补丁算法。
